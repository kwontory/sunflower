## D003 — 태양 위치 공개 API

날짜: 2026.09.27

결정:
주 API는 USNO Astronomical Applications API의 celnav 엔드포인트를 사용한다.
필요한 경우 NASA JPL Horizons API를 교차 검증용으로 사용한다.

판단:
나

이유:
USNO celnav는 태양의 방위각(`zn`)과 고도(`hc`)를 직접 제공하고,
API key가 필요 없으며 CORS를 허용(`access-control-allow-origin: *`)해 브라우저에서 바로 호출할 수 있다.
따라서 저장소에 비밀값을 둘 필요가 없다.

JPL Horizons는 공신력이 높지만 CORS 헤더가 없고 응답이 텍스트 표 형식이라
주 API보다는 교차 검증용으로 적합하다.

조사 시 공개 테스트 좌표(서울시청, 37.5663, 126.9779)로
2026-09-27 03:00 UTC 값을 비교한 결과 두 API가 일치했다.
(방위각 약 170.87°, 고도 약 50.46°)

참고:
- USNO 공식 문서: https://aa.usno.navy.mil/data/api
- JPL Horizons 공식 문서: https://ssd-api.jpl.nasa.gov/doc/horizons.html
- USNO celnav 시각 입력은 UT1 기준이다.
- 방위각·고도를 제공하지 않는 API(sunrise-sunset.org 등)는 제외했다.
- API key가 필요한 ipgeolocation.io는 비밀값 관리 부담 때문에 제외했다.

## D005 — API 호출 간격, 캐시, 재시도 정책

날짜: 2026.09.27

결정:
D004(API 호출 최소화)의 구체적인 정책을 다음과 같이 정한다.

### 호출 간격

- 페이지 진입 후 위치를 얻으면 1회 호출한다.
- 자동 갱신 간격은 5분이며, 탭이 보이는 동안에만 갱신한다. (Page Visibility API)
- 탭에 다시 돌아왔을 때는 마지막 정상값이 5분보다 오래된 경우에만 호출한다.
- 수동 새로고침은 직전 호출 후 60초 이내면 호출하지 않고 캐시를 사용한다.
- 위치 변화만으로는 재호출하지 않는다.

### 캐시

요청 캐시와 마지막 정상값을 분리한다.

- 요청 캐시
  - 키: 소수 둘째 자리로 반올림한 좌표 + UTC 분
  - 유효 시간: 5분
  - 캐시 값을 사용할 때는 캐시된 값임을 표시한다.
- 마지막 정상값
  - 검증을 통과한 응답만 저장한다.
  - 값, 조회 시각, 출처(USNO), 반올림 좌표를 함께 저장한다.
  - 호출이 실패해도 삭제하지 않는다.
  - 브라우저 저장소에 보관한다.
  - 조회 후 15분이 지나면 "오래된 값(stale)"으로 표시한다.
- KST 일별 기록은 마지막 정상값에서 날짜별로 저장하며, 기록을 위한 별도 호출은 하지 않는다.

### 좌표 반올림

외부 API 요청과 저장에는 소수 둘째 자리(약 1.1km)로 반올림한 좌표를 사용한다.

### 재시도

- 재시도 대상: 시간 초과(요청당 약 8초), 네트워크 오류, HTTP 5xx, HTTP 429
- 재시도 제외: HTTP 4xx(429 제외), 응답 형식 오류, 값 범위 이상
- 최대 2회 재시도(총 3회 시도), 약 2초 → 약 6초 간격에 무작위 지연(jitter)을 더한다.
- `Retry-After` 헤더가 있으면 따른다.
- 재시도가 모두 실패하면 마지막 정상값과 실패 상태를 함께 표시하고 다음 정기 호출까지 기다린다.
- 연속 실패 시 자동 갱신 간격을 5분 → 10분 → 20분 → 최대 30분으로 늘리고, 성공하면 5분으로 되돌린다.
- 탭이 가려진 동안에는 재시도하지 않는다.

### JPL Horizons 교차 검증

- 자동 호출하지 않고, 필요할 때만 호출한다.
- 재시도하지 않는다.
- CORS 미지원으로 서버 프록시가 필요하므로 기술 스택 결정 시 함께 정한다.

### 구현 방향

- 호출 스케줄, 캐시, 재시도는 외부 API 통신 코드와 분리하고, 현재 시각은 주입할 수 있게 한다.
- 조회한 값 사이를 로컬 계산으로 보간하지 않는다.

판단:
나

이유:
태양 방위각은 서울 기준 정오 무렵 가장 빠르게 변하며,
9월 말에는 약 0.4°/분, 하지에는 약 0.9°/분이다.
5분 간격이면 최악의 경우에도 오차가 약 5°로 휴대폰 나침반 센서 오차 수준이다.
시간당 호출은 탭당 최대 약 12회로 제한된다.

좌표 반올림으로 인한 방위각 오차는 약 0.01°로 무시할 수 있고,
정확한 GPS 좌표가 외부 API와 브라우저 저장소에 남지 않는다.

일시적 오류만 제한적으로 재시도하고 연속 실패 시 간격을 늘려,
외부 서비스 장애 중에도 호출이 과도하게 늘지 않게 한다.

값 사이를 로컬 계산으로 보간하면 외부 API 값과 계산 값이 섞여
실패한 외부 데이터를 정상처럼 보이지 않게 한다는 원칙이 흐려지므로 하지 않는다.

## D006 — 기술 스택

날짜: 2026.09.27

결정:

### 화면 구현

Vite + TypeScript로 구현하며, UI 프레임워크는 사용하지 않는다.

- 화면은 상태를 받아 그리는 `render(state)` 형태의 함수로 구성한다.
- 외부 API 통신, 응답 검증, 태양 방향 계산, 데이터 저장, 화면 상태와 UI 표시는 모듈 단위로 분리한다.

### 테스트

- Vitest를 사용한다.
- 호출 간격, 재시도, stale 판정은 가짜 타이머로 검증한다.
- 외부 실패 상황은 주입한 가짜 fetch로 재현한다.
- Playwright를 이용한 E2E 테스트는 나중에 추가한다.

### 저장소

- localStorage를 사용한다.
- 저장 모듈을 분리해 두고, 필요 시 IndexedDB로 전환한다.

### 배포처와 Horizons 프록시

- 교차 검증이 필요해지는 시점 또는 배포 시점에 함께 결정한다.
- 정적 파일만 제공하는 호스팅(GitHub Pages 등)은 Horizons 프록시를 둘 수 없다는 점을 고려한다.

판단:
나

이유:
USNO는 브라우저에서 직접 호출할 수 있어 서버 없이 정적 웹앱으로 구현할 수 있고,
사용자의 좌표가 우리 서버를 거치지 않는다.

화면 상태가 로딩, 정상, 캐시, stale, 실패 + 마지막 정상값 정도로 단순해
UI 프레임워크 없이도 충분하다.
프레임워크 규칙과 섞이지 않아 모듈 분리 원칙을 그대로 반영할 수 있고,
의존성이 적어 과제 5에서 AI 세션 간 인수인계와 고정 검사가 단순해진다.

TypeScript는 API 응답 검증 코드에 타입 안전장치를 제공한다.

Vitest는 Vite와 설정을 공유하고 가짜 타이머를 지원해
D005의 호출 간격, 재시도, stale 정책을 테스트하기 쉽다.

마지막 정상값과 KST 일별 기록은 데이터가 작고 단순해 localStorage로 충분하다.

## D007 — UI 구조

날짜: 2026.09.27

결정:
UI 구조 후보 중 A(나침반 다이얼 중심)와 C(탭 분리)를 조합한다.

- 첫 화면("지금" 탭)은 A의 나침반 다이얼을 중심으로 한다.
  - 다이얼은 기기 방향에 맞춰 회전하고, 해의 위치와 회전해야 할 각도를 표시한다.
  - 안내 문장(예: "오른쪽으로 32° 돌아보세요"), 방위각·고도, 데이터 상태와 출처를 함께 표시한다.
- 하단 탭으로 화면을 나눈다: 지금 / 기록 / 상태
  - 기록: KST 일별 기록과 서로 다른 날짜의 기록 비교
  - 상태: 데이터 상태, 출처, 조회 시각, 실패 내역
- 데이터 상태 표시는 시안의 5종(정상, 캐시된 값, 오래된 값, 실패 + 마지막 정상값, 방향 센서 없음)을 기준으로 한다.
  - 과제 4의 외부 실패 5종과 상태 표시의 대응은 구현 단계에서 결정한다.
- UI 서체는 명조(serif) 계열을 사용하지 않고 고딕(sans-serif) 계열을 사용한다.
- 로고는 워드마크 후보 1안으로 한다.
  - 서체: Sora SemiBold (SIL Open Font License)
  - 표기: 소문자 `sunflower`, 자간 약 -0.035em (작은 크기에서는 약 -0.03em)
  - 가운데 `o` 한 글자만 호박색으로 표시한다. (밝은 배경 `#B8680A`, 어두운 배경 `#F4B43C`)
  - 이미지나 아이콘 없이 서체만으로 구성한다.
- UI 본문 서체는 IBM Plex Sans KR로 한다. (IBM Plex Sans 계열의 한글 지원판, SIL Open Font License)
  - 제목과 큰 숫자도 같은 서체의 굵은 두께(600~700)를 사용한다.
  - 숫자는 자리 폭이 같은 숫자(tabular-nums)로 표시한다.
- 화면 헤더에는 로고 워드마크를 사용한다.
- 용어: 문서와 코드에서는 설계 용어를 쓰고, 화면에는 사용자 친화적인 말투를 쓴다.

  | 설계 용어 (문서·코드) | 화면 표기 |
  |---|---|
  | 정상 (fresh) | 실시간 |
  | 캐시 (cached) | 최근 값 |
  | stale | 오래된 값 |
  | 마지막 정상값 (last good value) | 마지막으로 받은 값 |
  | 외부 요청 실패 (timeout 등) | 원인별 안내 문장 (예: "응답이 늦어지고 있어요", "요청이 너무 많아요. 잠시 기다려 주세요", "불러오지 못했어요") |
  | 방향 센서 없음, 방향 권한 거부, 위치 권한 거부, 위치 확인 실패 | 방향 감지 안 됨 |

- 방향 센서 관련 원인과 위치 관련 원인은 화면에서 같은 "방향 감지 안 됨"으로 안내하되, 내용은 구분한다.
  - 방향 센서 없음·방향 권한 거부: 태양 데이터는 그대로 표시하고, 회전 각도 대신 방위(예: "남쪽(170.9°)을 바라보세요")로 안내한다.
  - 위치 권한 거부·위치 확인 실패: 태양 데이터를 받을 수 없으므로 값을 표시하지 않고, 위치 허용을 안내한다.
  - 문서와 코드에서는 두 원인을 서로 다른 상태로 구분한다.

- "실시간" 표기는 실제로는 5분 간격 갱신(D005)이므로, 항상 조회 후 경과 시간(예: "실시간 · 2분 전")을 함께 표시한다.
- 모바일, 태블릿(세로·가로), 데스크톱 시안을 "지금", "기록", "상태" 탭별로 작성했으며, 화면 크기별 세부 레이아웃은 구현 단계에서 조정한다.

판단:
나

이유:
해를 바라볼 방향을 알려주는 서비스의 첫인상은 다이얼이 가장 직관적으로 전달한다.
과제 4의 KST 일별 기록 비교와 데이터 상태는 첫 화면과 분리된 공간이 있어야 명확하게 보여줄 수 있다.

로고 1안은 Sora의 원형에 가까운 `o`에 색 하나만 더해 이미지 없이 해를 암시하므로 깔끔하고,
앱 헤더 크기(22px)에서도 형태가 유지된다.

## D008 — 배포처

날짜: 2026.09.27

결정:
배포처는 Vercel로 한다.

- 실기기 확인(T13)을 위해 HTTPS 주소가 필요해 Vercel에 배포했다.
- 배포에는 빌드에 필요한 파일만 올린다. (`.vercelignore` 허용 목록 방식)
- Horizons 교차 검증용 서버 프록시가 필요해지면 같은 Vercel 프로젝트의 서버리스 함수로 둔다.
- 공개 범위(Vercel 로그인 보호 유지 여부)와 운영 주소 사용 방식은 아직 확정하지 않는다.

판단:
나

이유:
위치·방향 센서는 HTTPS에서만 동작하므로, 인증서 경고 없이 어느 기기에서나 열 수 있는 주소가 필요하다.
로컬 HTTPS는 WSL2 환경에서 방화벽·포트 전달 설정과 기기별 인증서 허용이 필요하다.
Vercel은 정적 배포와 서버리스 함수를 함께 지원해 D006에서 미룬 Horizons 프록시 위치도 해결된다.

## D009 — JPL Horizons 교차 검증 제외

날짜: 2026.09.27

결정:
JPL Horizons 교차 검증은 하지 않는다. 외부 API는 USNO celnav 하나만 사용한다.

- 화면의 "JPL Horizons로 교차 검증" 버튼과 관련 문구를 없앤다.
- 서버 프록시를 두지 않는다. 배포는 정적 파일만으로 한다.
- D003·D005·D008의 Horizons 관련 내용은 이 결정으로 대체한다.

판단:
나

이유:
USNO 값은 조사 단계에서 Horizons와 소수 셋째 자리까지 일치했고(D003),
교차 검증을 위해 서버 프록시를 운영하는 부담에 비해 얻는 이점이 작다.
외부 호출도 한 곳으로 줄어 호출 최소화(D004)와 보안 정책(외부 연결은 USNO만 허용)에도 맞는다.

## D010 — 위치 확인 시간 단축

날짜: 2026.09.27

결정:
위치 확인이 오래 걸리는 문제(2차 실기기 확인)에 다음 세 가지를 적용한다.

- A. 마지막으로 받은 값의 반올림 좌표(약 1.1km)로 먼저 조회해 보여주고, 현재 위치는 동시에 확인한다.
  - 현재 위치가 같은 좌표면 다시 조회하지 않는다. 다르면 새 좌표로 다시 조회한다.
  - 위치 권한을 거부하면 이전 좌표도 쓰지 않고 위치 없음 상태로 바꾼다. 늦게 도착한 이전 좌표의 조회 결과도 버린다.
  - 위치를 잠시 못 잡은 경우(시간 초과 등)에는 이전 위치 기준 값을 계속 보여주고, 그 사실을 화면에 표시한다.
- B. 기기에 남아 있는 위치를 쓰는 허용 시간(`maximumAge`)을 10분에서 1시간으로 늘린다.
- C. 대기 문구를 단계별로 보여준다: "위치를 확인하고 있어요" → "해의 위치를 받아오고 있어요".
  이전 위치 기준일 때는 "이전 위치 기준 · 현재 위치 확인 중"을 표시한다.

판단:
나

이유:
재방문 시 기기가 위치를 새로 잡는 동안(수 초~수십 초) 화면이 멈춘 것처럼 보였다.
해의 방향은 수 km 이동해도 0.1° 수준으로만 달라지므로 이전 반올림 좌표로 먼저 보여줘도 안내에 영향이 거의 없다.
새로 저장하는 정보는 없고, 이미 저장된 반올림 좌표만 사용한다.

## D011 — 운영 주소와 보안 헤더

날짜: 2026.09.27

결정:

- 운영 대표 주소는 `https://sunflower-gamma-two.vercel.app`로 한다.
- 배포 응답에 보안 헤더를 붙인다. (`vercel.json`)
  - `X-Frame-Options: DENY`, `Content-Security-Policy: frame-ancestors 'none'` — 다른 사이트가 앱을 iframe으로 끼워 넣지 못하게 한다.
  - `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`
  - `Permissions-Policy` — 위치·방향 센서는 이 사이트에서만 쓰고, 카메라·마이크 등은 쓰지 않는다.
  - `Cross-Origin-Opener-Policy: same-origin`
  - `Access-Control-Allow-Origin`은 Vercel 기본값(`*`) 대신 운영 대표 주소만 허용한다.
  - `/sw.js`는 `Cache-Control: no-cache`로 새 배포가 바로 반영되게 한다.
- 페이지 안의 보안 정책(CSP)에서 개발용으로 넣었던 WebSocket 허용(`ws: wss:`)을 없앤다. 외부 연결은 USNO만 허용한다.

판단:
나

이유:
전체 보안 점검에서 클릭재킹 방지 설정이 없고, CSP의 연결 허용 범위가 필요 이상으로 넓은 것을 확인했다.
`<meta>` CSP는 `frame-ancestors`를 지원하지 않아 응답 헤더로만 막을 수 있다.
앱을 다른 출처에서 불러갈 일이 없으므로 교차 출처 허용도 운영 주소로 좁힌다.

## D012 — 심야에 해 항목이 없는 USNO 응답

날짜: 2026.09.27

결정:

- USNO celnav가 HTTP 200으로 응답했고 `properties.data`에 다른 천체 항목(이름과 `almanac_data`가 있는 항목)이 1개 이상 있는데
  `Sun` 항목만 없으면, 실패가 아니라 "해 없음"(`sun-absent`)으로 처리한다.
  - `data`가 비어 있거나, 다른 천체 항목도 형식이 맞지 않거나, `{"error"}` 응답이면 지금처럼 `invalid-response` 실패로 둔다.
  - 네트워크 오류·시간 초과·HTTP 오류의 처리(재시도, 백오프)는 바꾸지 않는다.
- 해 없음은 연속 실패로 세지 않는다. 자동 갱신은 기본 5분 간격을 유지해 해가 뜨면 바로 반영한다.
- 해 없음은 마지막 정상값과 KST 일별 기록을 바꾸지 않는다. 마지막 정상값은 "마지막으로 받은 값" 캡션을 붙여 흐리게 보여준다.
- 해 없음 상태와 해 고도 0° 이하에서는 나침반 대신 달 그림을 보여준다.
  이 그림은 장식이며 방위·회전 정보가 없고, 실제 달의 위상·위치와 관계없다.
- 외부 요청 실패 중에는 마지막 정상값의 고도와 관계없이 회전·방위 안내를 하지 않는다.
- 60초 안의 새로고침은 호출하지 않고, 실패·해 없음 상태를 마지막 정상값으로 덮어쓰지 않는다.

판단:
나 (Claude Code 제안 후 승인)

이유:
2026-09-27 00:00 KST 서울시청 좌표로 실제 호출해 보니 HTTP 200, 달·행성·항성 31개가 있고 `Sun` 항목만 없었다.
이 경우를 실패로 처리하면 심야 내내 "불러오지 못했어요"와 백오프가 쌓이고,
낮에 받은 마지막 정상값으로 "왼쪽으로 N°" 같은 방향 안내가 나올 수 있었다.
판정 조건을 "다른 천체 항목은 정상"으로 좁힌 것은 USNO 응답 형식이 바뀐 경우를 심야로 잘못 보지 않기 위해서다.
